# Music ConnectZ on iOS — native SwiftUI, built without a Mac

Everything here is real and in the repo. Where something isn't built yet it says
so plainly, because a checklist that lies is worse than no checklist.

**What this is:** a native SwiftUI app in `ios/`, talking to the same REST API
the web app uses. Not a WebView. That distinction is the whole reason the app
has a chance at getting approved — see [§1](#1-why-native-and-not-the-android-trick).

---

## 1. Why native, and not the Android trick

The Android app is a **Trusted Web Activity** — a thin shell that opens
`musicconnectz.net` full-screen. Google explicitly sanctions that. **Apple does
not.** There is no TWA equivalent on iOS, and
[guideline 4.2 (minimum functionality)](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)
is the single most common rejection for exactly this: an app that is "simply a
song or movie... or a repackaged website."

So iOS gets real native screens. The expensive half of that work — the API — was
already done, which is the only reason this is a reasonable amount of effort.

**Built:** auth (three ways), the tour, PersonaZ browsing, the BodieZ library
with server-side equipment filtering, account screen with deletion.

**Not built yet:** the feed, uploads, messaging, wallet, MerchZ, BodieZ session
logging, push notifications, In-App Purchase. The IAP one matters most — see
[§7](#7-the-thing-that-will-cost-you-30).

## 3. Building it with no Mac

`.github/workflows/ios.yml` is your Mac. Two jobs:

| Job | Needs an Apple account? | What it does |
|---|---|---|
| `build` | **No** | Compiles and runs the tests on a simulator. Runs on every push to `ios/**`. |
| `testflight` | Yes | Archives, signs in the cloud, uploads to TestFlight. Manual trigger only. |

Push the branch and the `build` job runs immediately — no signup, no $99, no
secrets. **That job is the first real compile of this code.** I wrote it on
Linux where no Swift compiler or iOS SDK exists, so expect to fix a few
compile errors on the first run; that's what the job is for. Everything in it
was written against the actual API shapes, which is the part that's hard to fix
later.

The `.xcodeproj` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from `ios/project.yml` and never committed. A hand-maintained `pbxproj` is a
file only Xcode can edit sanely, and you don't have Xcode. Adding a Swift file
needs no edit to `project.yml` — the whole directory is globbed.

## 4. Getting to TestFlight

1. **Apple Developer Program** — $99/yr,
   [enroll here](https://developer.apple.com/programs/enroll/). Individual
   enrollment is same-day-ish; Organization needs a D-U-N-S number and takes
   longer. This is separate from your $25 Google Play fee.
2. **App ID** — `APPLE_OAUTH.md` §1 already has you creating
   `net.musicconnectz.app` with Sign In with Apple enabled. Same bundle ID this
   app uses. Nothing new to do.
3. **App Store Connect record** — [appstoreconnect.apple.com](https://appstoreconnect.apple.com)
   → Apps → **+** → New App, pick that bundle ID.
4. **App Store Connect API key** — Users and Access → Integrations → **+**.
   Role: **App Manager**. Download the `.p8` **once** (Apple never shows it
   again). Then add four repo secrets under Settings → Secrets → Actions:

   | Secret | Where it comes from |
   |---|---|
   | `APP_STORE_CONNECT_KEY_ID` | The key's ID, shown in the list |
   | `APP_STORE_CONNECT_ISSUER_ID` | Top of the Integrations page |
   | `APP_STORE_CONNECT_KEY_P8` | `base64 -i AuthKey_XXXX.p8` — the whole thing |
   | `APPLE_TEAM_ID` | Top-right of developer.apple.com |

5. Actions → **iOS** → Run workflow → tick **upload**.

Signing is done by Xcode itself via `-allowProvisioningUpdates` with that API
key. There are no `.p12` certificates to export from a machine you don't own —
that's the part that usually blocks a Mac-less iOS build, and it's solved.

## 5. Backend change this needed

Native Sign in with Apple **was broken against your backend** and is now fixed.

Apple mints a different audience depending on where the user signed in: the
**Services ID** (`net.musicconnectz.web`) for web, the **Bundle ID**
(`net.musicconnectz.app`) for a native iOS app. `verify_apple` only accepted the
Services ID, so every native sign-in would have failed with "Apple rejected that
sign-in token" — and the error message would have sent you hunting for a key
problem that didn't exist.

It now accepts both, and `apps/accounts/test_apple_oauth.py` proves it still
rejects a token minted for somebody else's app. **Set this on Render:**

```
APPLE_OAUTH_BUNDLE_ID=net.musicconnectz.app
```

Without it, native sign-in fails closed. That's deliberate — an unset audience
means we can't verify the token was minted for us, and accepting it anyway would
let anyone with any Apple token sign in as anyone.

## 6. App Review items that are already handled

- **In-app account deletion** (required for any app with sign-up; a support
  email or website link is an explicit rejection) — `AccountView` calls
  `POST /api/economy/account/delete/` behind a confirm alert.
- **Sign in with Apple** (guideline 4.8 — required once you offer any other
  social login, and you offer Google and GitHub) — native, on the sign-in screen.
- **App icon with no alpha** — App Store Connect rejects a transparent icon
  outright, and your Play icon is RGBA. `tools/make_brand_assets.py` now emits a
  separate flattened RGB icon for iOS from the same geometry, so the two can't
  drift. Also unrounded: iOS applies its own mask, and a pre-rounded source gets
  rounded twice and looks pinched.
- **No ATS exceptions** — the API is HTTPS throughout, so `Info.plist` has none.
  Adding `NSAllowsArbitraryLoads` invites a review question with no good answer.
- **Privacy policy URL** — required. Same one Play needs; still owed a page.

## 7. The thing that will cost you 30%

**Apple takes 15–30% of digital goods sold in an iOS app, and requires you to
use In-App Purchase for them.** Your economy sells PromptZ and membership tiers.
On iOS those are digital goods. You cannot take Stripe or PayPal for them inside
the app, and you cannot link out to a web checkout for them either
([guideline 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)).

This is not a thing to discover at review. Three honest options:

1. **Implement StoreKit 2 IAP** for PromptZ and tiers, and add a server-side
   receipt verification endpoint — the mirror of `play_billing.py`, which
   already exists for Android and is the model to copy.
2. **Ship v1 without any purchasing on iOS.** Members buy on web or Android; the
   iOS app just uses what they have. This is legitimate and gets you approved
   fastest — the app must simply not mention or link to outside purchasing.
3. **Reader-app style exemption** — doesn't apply here; you're not a
   Netflix/Kindle-shaped catalogue app.

**MerchZ print-on-demand is different and is fine.** Physical goods shipped to a
buyer are explicitly exempt from IAP — that stays on your existing payment rail
at 0% to Apple.

My recommendation is **option 2 for v1**. Get approved, get TestFlight running,
then add StoreKit deliberately rather than under review pressure.

## 8. Screenshots for the listing

**Actions → iOS → Run workflow → tick `screenshots`.** Download them from the
run's Artifacts. That's the whole flow.

It runs `ios/UITests/ScreenshotTests.swift` against the real app in a simulator
and captures six screens: sign-in, the tour, PersonaZ, a persona's skills,
BodieZ, and Account. The **simulator device is the screenshot size**, so the job
runs a matrix:

| Simulator | Pixels | App Store slot |
|---|---|---|
| iPhone 11 Pro Max | 1242×2688 | 6.5" |
| iPhone 15 Pro Max | 1290×2796 | 6.9" |

Every PNG is size-checked before upload. App Store Connect rejects an off-size
file with an error that doesn't name it; the job names it.

**Optional secrets** — `MCZ_UITEST_USER` and `MCZ_UITEST_PASSWORD`, a real
account on the live backend. Without them the job still runs and still produces
the sign-in shot; it just can't get past the login screen. Use the same account
you give App Review as test credentials.

Two things to know:

- **Login happens through the actual UI**, typing into the real fields. No test
  backdoor in the app, and it means a broken sign-in fails the screenshot job
  instead of quietly producing a screenshot of a broken sign-in.
- `tools/store_shots.py` still exists and still captures the **web** app at the
  same sizes. It's the right tool for the Play listing and for marketing pages —
  but not for this listing, because an App Store listing has to show the app
  you're actually shipping.

## 9. Honest state of it

This is a scaffold with real working parts, not a finished app. What's solid:
the API client, token handling, auth including Apple, and the data models —
all written against the actual endpoints, with the response shapes checked
rather than assumed. Three shapes I had guessed wrong got caught that way
(`CatalogEntry` sends `name`/`emoji` not `label`; the tour's reply nests its
text under `explain` and returns the whole next step; and tour completion lives
on the tour's own progress, not `user.onboarded` — routing on that flag would
have replayed the tour forever for anyone who skipped).

What's unproven: **none of this Swift has been compiled.** There is no Swift
toolchain or iOS SDK on Linux. The `build` job is the first compile, and it's
free to run.
